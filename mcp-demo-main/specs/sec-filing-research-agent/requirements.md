# 需求規格：SEC Filing Research Agent

## 1. 文件狀態

- 規格名稱：`sec-filing-research-agent`
- 階段：已核准（2026-09-23）
- 目標：規劃一套可完整展示資料下載、RAG 與 MCP 協作的 SEC 財報研究 Demo
- 規範語法：所有驗收條件均採用 EARS（Easy Approach to Requirements Syntax）

## 2. 目標與使用者

本 Demo 面向需要研究美國上市公司公開申報文件的技術展示者與研究使用者。系統應以 SEC 官方資料為唯一研究語料來源，下載並整理多家公司、多期 10-K 與 10-Q，將敘事內容交由 RAG 檢索，將財務數字交由 SEC XBRL 結構化資料工具處理，再由研究代理透過 MCP 完成查詢規劃、工具呼叫、跨期比較與具引用的答案。

成功的 Demo 應能清楚展示：

1. 官方資料如何被安全、可重跑地下載與更新。
2. SEC HTML 如何轉換成具有章節與時間 metadata 的 RAG 語料。
3. 敘事型問題與數值型問題為何需要不同資料路徑。
4. MCP 如何標準化 RAG、XBRL 與最新申報查詢工具。
5. 研究答案如何被限制在 SEC 官方資料並追溯至原始 filing。

## 3. 已核准的能力地圖

| 模組 ID | 責任 | 依賴 |
|---|---|---|
| `sec-data-pipeline` | 公司代碼解析、申報清單、HTML／XBRL 下載、原始資料保存、增量同步與 SEC 公平存取限制 | 無 |
| `filing-rag` | HTML 清理、章節辨識、切塊、metadata、向量化、混合檢索、重排與引用定位 | `sec-data-pipeline` |
| `sec-mcp-server` | 透過 MCP 提供申報搜尋、原文取得、最新申報與 XBRL 財務指標等工具 | `sec-data-pipeline`、`filing-rag` |
| `research-agent` | 判斷敘事型或數值型問題、呼叫 MCP 工具、跨期比較、限制 SEC-only corpus 並產生可追溯答案 | `sec-mcp-server` |
| `demo-experience` | 最小可用的互動介面、示範問題、處理狀態、工具軌跡與來源引用呈現 | `research-agent` |

建置順序：`sec-data-pipeline → filing-rag → sec-mcp-server → research-agent → demo-experience`

## 4. 已確認的範圍與前提

1. 預設公司為 Apple（AAPL）、Microsoft（MSFT）與 NVIDIA（NVDA）。
2. 預設歷史範圍為執行建置時最近五個已完成會計年度。
3. RAG corpus 納入 10-K 與 10-Q；第一版不索引 8-K、修正版 filing、附件或代理委託書。
4. 最新 filing 工具可即時查詢 8-K metadata，但不將 8-K 全文納入第一版 RAG corpus。
5. 財務數值優先使用 SEC XBRL API，不從向量檢索結果推測數字。
6. Demo 為單一研究使用者情境，不包含帳號、權限、多租戶、投資交易或投資建議。
7. 回答預設使用繁體中文；SEC 原文引用保留英文並提供來源資訊。
8. 模型、向量資料庫、嵌入模型與 MCP 傳輸方式留待設計階段決定。

## 5. 使用者故事與 EARS 驗收條件

### US-01：設定研究資料範圍

身為 Demo 操作者，我希望能指定公司、表單類型與期間，使 corpus 的邊界明確且可重現。

- `AC-01.1`【普遍】系統應保存每次 corpus 建置所使用的公司、CIK、ticker、表單類型、期間與建置時間。
- `AC-01.2`【事件】當操作者未提供資料範圍時，系統應採用 AAPL、MSFT、NVDA、最近五個已完成會計年度及 10-K／10-Q 的預設範圍。
- `AC-01.3`【條件】若輸入的 ticker 無法對應至唯一 CIK，則系統應拒絕啟動下載並回報可理解的驗證錯誤。
- `AC-01.4`【事件】當資料範圍被確認時，系統應產生可供後續下載、索引與評估共同使用的不可含糊範圍描述。

### US-02：下載 SEC 官方申報資料

身為 Demo 操作者，我希望系統能由 SEC 官方端點取得申報 metadata、原始 HTML 與 XBRL，使資料來源權威且不依賴付費供應商。

- `AC-02.1`【事件】當歷史回填開始時，系統應先由 SEC 官方 ticker／CIK 與 submissions 資料取得符合範圍的 filing 清單。
- `AC-02.2`【事件】當 filing 清單包含符合範圍的新 accession number 時，系統應下載該 filing 的主要 HTML 文件與必要 metadata。
- `AC-02.3`【事件】當需要財務數值資料時，系統應由 SEC 官方 XBRL API 取得 company facts 或指定 concept 資料。
- `AC-02.4`【狀態】當系統存取 SEC 官方端點時，系統應宣告符合 SEC 指引的 User-Agent，並將總請求速率限制在每秒 10 次以下。
- `AC-02.5`【異常】若 SEC 回應限流、暫時性伺服器錯誤或網路失敗，則系統應保留已完成進度、延後重試並記錄失敗原因。
- `AC-02.6`【異常】若下載內容不符合預期類型或無法驗證 filing identity，則系統應隔離該資料且不得送入 corpus。
- `AC-02.7`【普遍】系統應保存每份 filing 的 CIK、ticker、公司名稱、form、filing date、period end、accession number、primary document 與 SEC 原始網址。

### US-03：重跑與增量同步

身為維護者，我希望資料管線可重跑且只處理新資料，使 Demo 能可靠更新而不產生重複內容。

- `AC-03.1`【事件】當相同 accession number 再次出現時，系統應辨識既有資料且不得建立重複 filing、section 或 chunk。
- `AC-03.2`【事件】當增量同步開始時，系統應僅下載尚未成功處理或已被 SEC 更新的 filing。
- `AC-03.3`【異常】若一次同步中途失敗，則系統應允許下次執行由最後可驗證狀態繼續。
- `AC-03.4`【事件】當同步完成時，系統應輸出新增、更新、略過、隔離與失敗的數量摘要。

### US-04：建立章節化 RAG corpus

身為研究使用者，我希望 filing 依正式章節整理，使檢索能針對 Risk Factors、MD&A 等語意區域，而不是盲目切割全文。

- `AC-04.1`【事件】當主要 HTML 文件完成下載時，系統應移除不屬於研究正文的導覽、重複目錄、樣式與無意義標記。
- `AC-04.2`【事件】當系統處理 10-K 時，系統應辨識至少 Item 1、Item 1A、Item 1C、Item 7 與 Item 8 的實際正文邊界。
- `AC-04.3`【事件】當系統處理 10-Q 時，系統應辨識至少 Part I Item 1、Part I Item 2 與 Part II Item 1A 的實際正文邊界。
- `AC-04.4`【異常】若章節只能在目錄中找到或無法可靠辨識正文邊界，則系統應標示解析失敗且不得把不確定內容偽裝成已辨識章節。
- `AC-04.5`【事件】當章節被切分成 chunks 時，系統應在每個 chunk 保存公司、CIK、ticker、form、filing date、period end、accession number、章節、chunk 順序與來源網址。
- `AC-04.6`【普遍】系統應保留從 chunk 回溯至原始 filing、原始章節及相鄰 chunk 的關聯。
- `AC-04.7`【事件】當 corpus 建置完成時，系統應輸出 filing、成功章節、失敗章節、chunks 與索引版本的摘要。

### US-05：依 metadata 與內容檢索 filing

身為研究使用者，我希望能以公司、期間、form 與章節限制搜尋，使結果只來自問題指定的官方 corpus。

- `AC-05.1`【事件】當研究問題指定公司、期間、form 或章節時，系統應在文字相似度排序前套用相應 metadata 篩選。
- `AC-05.2`【事件】當研究問題未明確指定必要範圍時，系統應由已設定的 Demo corpus 邊界推導範圍並在答案中揭露。
- `AC-05.3`【事件】當檢索執行時，系統應同時支援關鍵字與語意相關性的候選結果。
- `AC-05.4`【事件】當候選結果產生時，系統應回傳可供代理比較的排序證據、metadata 與引用定位資訊。
- `AC-05.5`【異常】若指定範圍內沒有足夠證據，則系統應回傳證據不足狀態且不得擴張至非 SEC 來源。

### US-06：透過 MCP 提供標準化研究能力

身為 MCP client，我希望能發現並呼叫具明確契約的 SEC 研究能力，使代理不需要知道內部資料庫或下載實作。

- `AC-06.1`【事件】當 MCP client 建立連線並要求能力清單時，MCP Server 應回傳可用工具、輸入 schema、輸出 schema 與用途說明。
- `AC-06.2`【普遍】MCP Server 應至少提供 filing 清單／最新申報、敘事內容搜尋、指定 filing 或章節讀取、XBRL 財務指標查詢及 corpus 狀態能力。
- `AC-06.3`【事件】當 MCP client 提供有效參數時，MCP Server 應回傳結構化結果、來源識別與可判斷的成功狀態。
- `AC-06.4`【異常】若 MCP client 提供無效公司、期間、form、metric 或 pagination 參數，則 MCP Server 應回傳結構化錯誤且不得執行部分含糊查詢。
- `AC-06.5`【異常】若下游 SEC 或 RAG 服務不可用，則 MCP Server 應區分暫時性依賴失敗、找不到資料與輸入錯誤。
- `AC-06.6`【普遍】MCP Server 應使公開能力與內部管理能力分離，且不得透過研究工具暴露秘密、主機路徑或未清理的例外內容。

### US-07：查詢結構化財務數值

身為研究使用者，我希望數值問題由 XBRL 資料回答，使結果具有單位、期間與 filing context。

- `AC-07.1`【事件】當問題要求營收、研發費用、淨利、資產或其他支援的財務指標時，研究代理應使用 XBRL 財務工具而非從 RAG 文字猜測數值。
- `AC-07.2`【事件】當財務工具回傳數值時，系統應同時回傳 taxonomy、concept、value、unit、fiscal year、fiscal period、form、filed date 與 accession number。
- `AC-07.3`【異常】若同一指標存在不同單位、期間或重複 facts，則系統應揭露選擇依據或要求縮小查詢，不得靜默混合。
- `AC-07.4`【異常】若公司僅提供無法安全對應的自訂 taxonomy，則系統應回報該指標無法正規化且不得自行推測對應。

### US-08：完成敘事、數值與複合研究問題

身為研究使用者，我希望代理能選擇正確工具並綜合多期證據，使回答同時具分析價值與可驗證性。

- `AC-08.1`【事件】當問題屬於敘事內容比較時，研究代理應使用 filing RAG 能力取得指定公司、期間與章節的證據。
- `AC-08.2`【事件】當問題屬於純數值查詢時，研究代理應使用 XBRL 財務能力並避免不必要的全文檢索。
- `AC-08.3`【事件】當問題同時包含敘事與數值分析時，研究代理應分別取得 RAG 與 XBRL 證據後再產生綜合結論。
- `AC-08.4`【事件】當問題要求跨期比較時，研究代理應逐期列出已找到與缺少的 filing，且不得把缺少期間視為沒有變化。
- `AC-08.5`【異常】若工具結果彼此衝突或不足以支持結論，則研究代理應揭露衝突或不確定性並限制結論強度。
- `AC-08.6`【普遍】研究代理應將系統輸出定位為研究資訊，而非投資建議、價格預測或交易指令。

### US-09：提供逐項可追溯引用

身為研究使用者，我希望每個重要結論都能回到 SEC 原始 filing，使我可以快速核對代理是否正確解讀資料。

- `AC-09.1`【事件】當答案提出 filing 內容相關的重要事實或比較結論時，系統應附上至少一個直接支持該敘述的 SEC 引用。
- `AC-09.2`【事件】當引用來自 RAG chunk 時，系統應顯示公司、form、filing date、period end、accession number、章節與 SEC 原始網址。
- `AC-09.3`【事件】當引用來自 XBRL fact 時，系統應顯示 concept、期間、單位、form、filed date 與 accession number。
- `AC-09.4`【異常】若系統無法產生可解析至 SEC 官方資料的引用，則系統應省略未受支持的斷言或明確標示為無法驗證。
- `AC-09.5`【普遍】系統不得把搜尋摘要、模型記憶、第三方新聞或財經網站標示成 SEC 官方引用。

### US-10：展示可理解的 Demo 體驗

身為 Demo 觀眾，我希望能看見問題、工具選擇、處理狀態與來源，使 RAG 和 MCP 的角色可以被清楚說明。

- `AC-10.1`【普遍】Demo 介面應提供自然語言輸入、繁體中文答案、引用清單與錯誤狀態。
- `AC-10.2`【事件】當研究代理呼叫 MCP 工具時，Demo 介面應顯示經清理的工具名稱、用途、狀態與耗時，且不得顯示秘密或完整內部提示詞。
- `AC-10.3`【事件】當答案完成時，Demo 介面應區分 RAG 敘事證據、XBRL 數值證據與代理綜合結論。
- `AC-10.4`【普遍】Demo 應內建至少一題跨年度 Risk Factors 比較、一題財務指標趨勢及一題同時使用 RAG 與 XBRL 的複合問題。
- `AC-10.5`【異常】若 corpus 尚未建置、MCP Server 未連線或必要服務不健康，則 Demo 介面應阻止誤導性查詢並指出缺少的條件。

### US-11：驗證資料品質與研究品質

身為維護者，我希望有可重複的驗證資料與檢查，使 Demo 不只是在單一範例上看似正確。

- `AC-11.1`【普遍】系統應提供涵蓋 metadata 篩選、章節檢索、跨期比較、XBRL 指標、複合工具呼叫、無結果與錯誤輸入的固定評估案例。
- `AC-11.2`【事件】當資料管線測試重跑相同範圍時，系統應證明 filing、section 與 chunk 數量不因重跑而重複增加。
- `AC-11.3`【事件】當 MCP 契約測試執行時，系統應驗證能力發現、合法呼叫、非法參數、下游失敗與結構化輸出。
- `AC-11.4`【事件】當研究品質評估執行時，系統應分別報告檢索命中、metadata 範圍正確性、引用可解析性與答案證據支持度。
- `AC-11.5`【狀態】當任何引用無法解析至 SEC 官方來源或答案使用範圍外來源時，該評估案例應判定失敗。
- `AC-11.6`【事件】當正式展示前驗證完成時，系統應輸出資料版本、模型與索引設定、測試結果及尚未驗證的限制。

### US-12：保護秘密並提供必要可觀測性

身為維護者，我希望系統能留下足以診斷問題的紀錄，同時避免洩漏秘密與使用者內容。

- `AC-12.1`【普遍】系統應記錄每次同步、解析、索引、檢索與 MCP 工具呼叫的 request ID、結果狀態、耗時與非敏感錯誤摘要。
- `AC-12.2`【普遍】系統不得將 API 金鑰、完整環境變數、認證標頭或秘密值寫入日誌、介面、規格或版本控制。
- `AC-12.3`【事件】當外部依賴發生錯誤時，系統應提供可供操作者定位階段與失敗類型的訊息，且不得回傳原始堆疊中的敏感資訊。
- `AC-12.4`【事件】當 Demo 啟動時，系統應檢查 corpus、索引、MCP 與模型依賴的健康狀態並呈現結果。

## 6. 非功能需求

- `NFR-01`【普遍】系統應能在單一開發工作站上完成預設 Demo corpus 的下載、處理、索引與查詢。
- `NFR-02`【普遍】系統應將原始資料、解析結果、索引資料與執行設定分離，使任一階段可被獨立重建。
- `NFR-03`【普遍】系統應使資料來源、解析版本、索引版本與模型設定可被記錄，以支援結果重現。
- `NFR-04`【事件】當 corpus 或索引版本改變時，系統應避免把不同版本的檢索結果混入同一次研究回答。
- `NFR-05`【普遍】系統應支援 Windows 開發環境，並以可攜方式描述本機執行所需的外部服務。
- `NFR-06`【普遍】系統應優先使用最少且可替換的基礎元件，不得為 Demo 引入分散式佇列、搜尋叢集或多租戶平台。
- `NFR-07`【事件】當完整 Demo 查詢完成時，系統應記錄端到端耗時與各工具耗時，以建立實測基準而非宣稱未驗證的效能 SLA。

## 7. 範圍外項目

以下項目不屬於第一版 Demo：

1. 全市場、S&P 500 或數萬份 filing 的大規模資料平台。
2. 8-K 全文、附件、影像、PDF OCR 與 legacy paper filing 的完整索引。
3. 跨公司自訂 XBRL taxonomy 的完整會計語意正規化。
4. 即時股價、新聞、分析師報告、社群資料或一般 Web Search。
5. 投資組合、交易執行、投資建議、價格預測或法規遵循認證。
6. 使用者帳號、企業 SSO、多租戶、權限後台與公開網際網路部署。
